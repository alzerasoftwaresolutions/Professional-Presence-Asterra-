# 1. Purpose

The Project / Case Study Detail page transforms a portfolio entry into **credible evidence of Asterra's work**.

The page should allow a visitor to understand:

* What the project was
* Who/what it was for, where appropriate
* The context or challenge
* Asterra's role
* The work delivered
* The outcome or result
* Relevant capabilities
* Related projects

The page should feel **documentary, precise, and evidence-driven**.

# 3. Project Hero

```text id="q5n8v2"
┌──────────────────────────────────────────────────────┐
│ PROJECT / SECTOR                                      │

│ Project Name                                         │
│                                                      │
│ Short project positioning statement                  │
│                                                      │
│ Location / Status / Business Unit                    │
│                                                      │
├──────────────────────────────────────────────────────┤
│                                                      │
│              LARGE PROJECT IMAGE                     │
│                                                      │
└──────────────────────────────────────────────────────┘
```

The hero image should be the strongest available authentic project image.

---

# 4. Hero Hierarchy

```text id="j8m4c6"
PROJECT / CASE STUDY
       ↓
PROJECT NAME
       ↓
SHORT POSITIONING STATEMENT
       ↓
PROJECT METADATA
       ↓
PRIMARY IMAGE
```

The project name should remain the strongest textual element.

---

# 5. Hero Image

Use:

* High-quality project photography
* Strong architectural or contextual composition
* Authentic project documentation
* Appropriate image dimensions

The image should communicate the project before the visitor reads the detailed content.

---

# 6. Project Metadata

A concise metadata block can appear beneath the hero title.

Possible fields:

```text id="s3k7v9"
Sector
Business Unit
Location
Project Status
Project Type
```

Only include fields that are available and useful.

Do not fabricate missing metadata.

---

# 7. Project Overview

The first major section should provide a concise project summary.

```text id="h6p2q8"
PROJECT OVERVIEW

Large statement

Supporting description.
```

This should answer:

> What was this project and what role did Asterra have?

---

# 8. Project Information Panel

A structured information panel can accompany the overview.

```text id="m4z8x1"
PROJECT INFORMATION

Client        —
Location      —
Sector        —
Scope         —
Status        —
```

Use only approved information.

Sensitive client information should not be displayed unless authorized.

---

# 9. Context / Challenge

If the project has a meaningful challenge, explain it.

```text id="v7q3n5"
THE CONTEXT

What needed to be addressed?

Supporting narrative explaining
the project's context.
```

This transforms the page from a portfolio image into a case study.

---

# 10. Approach / Scope

Explain what Asterra actually contributed.

```text id="c9m5k2"
OUR ROLE

01  Scope / Capability
    Description

02  Scope / Capability
    Description

03  Scope / Capability
    Description
```

Focus on the actual work.

Avoid vague marketing language.

---

# 11. Scope Visualization

Where appropriate, use a structured visual:

```text id="p8j4r6"
PROJECT SCOPE

Research ── Planning ── Design ── Delivery
```

The actual stages should reflect the project's real process.

Do not impose a generic four-step process on every project.

---

# 12. Project Gallery

The gallery should provide visual evidence.

Possible layout:

```text id="n6v8c2"
┌──────────────────────────┐ ┌──────────────┐
│                          │ │              │
│      Large Image         │ │ Small Image  │
│                          │ │              │
└──────────────────────────┘ └──────────────┘

┌──────────────┐ ┌──────────────────────────┐
│ Small Image  │ │                          │
│              │ │      Large Image         │
└──────────────┘ └──────────────────────────┘
```

The gallery should remain editorial rather than looking like a social-media photo grid.

---

# 13. Gallery Rules

Use only meaningful images.

Avoid:

* Duplicate photographs
* Near-identical angles
* Low-quality images
* Unrelated stock imagery
* Excessive gallery length

A smaller selection of strong images is preferable.

---

# 14. Image Captions

Captions may be used when an image requires context.

Example:

```text id="f5q9m3"
Project exterior during completion phase.
```

Captions should add information, not repeat the project name.

---

# 15. Outcome / Impact

If verified project results exist, give them strong visual emphasis.

```text id="z8k4p1"
PROJECT OUTCOME

Large result statement

Supporting explanation
```

Potential evidence can include:

* Completed scope
* Delivered facility
* Measurable result
* Operational improvement
* Project milestone

Only use measurable claims when verified.

If meaningful metrics exist:

```text id="q7v3m8"

PROJECT METRIC

02
PROJECT METRIC

03
PROJECT METRIC
```

Do not create artificial statistics simply to make the case study visually impressive.

---

# 17. Testimonial

Optional.

If an authorized client testimonial exists:

```text id="k5m9x2"
“Approved client statement.”

Client / Organization
```

Use authentic attribution.

Do not generate fictional testimonials.

# 18. Related Capability

Every case study should connect back to the relevant business capability when a genuine relationship exists.

```text id="r6p4n8"
RELATED CAPABILITY

Business Unit Name

Short description

Explore capability →
```

This creates the relationship:

**Project → Capability**

---

# 19. Related Projects

A small selection can appear near the end.

```text id="w8c5j3"
RELATED PROJECTS

Project A       Project B       Project C
```

Use projects that share:

* Business unit
* Sector
* Project type
* Similar capability

The relationship should be meaningful.

---

# 20. Project Navigation

Optional previous/next navigation:

```text id="j4q7s8"
← Previous Project

Back to Projects

Next Project →
```

This is particularly useful for larger portfolios.

---

# 21. Contact CTA

The final CTA should connect evidence to engagement.

```text id="x6m2v9"
HAVE A SIMILAR REQUIREMENT?

Short supporting statement.

[Contact Asterra →]
```

This is more contextually relevant than a generic:

**"Let's work together."**

Understand Asterra's role

See evidence
  ↓
Explore capability

This is the intended conversion path.

# 24. Content Width

Case-study narrative should use a comfortable reading width.

For long content:

```text id="h5q8m2"
┌─────────────────────────────────────┐
│                                     │
│        Comfortable reading          │
│        column                       │
│                                     │
└─────────────────────────────────────┘
```

Avoid full-width paragraphs.

Use wider layouts primarily for imagery and structured information.

# 28. Accessibility

Required:

* Meaningful alt text
* Semantic headings
* Keyboard-accessible navigation
* Accessible gallery controls
* Visible focus states
* Sufficient contrast
* Descriptive links

If a lightbox is used, it must be keyboard accessible and provide a clear close mechanism.

# 30. Search Intent

The page primarily serves:

* Commercial investigation
* Brand research
* Project research
* Capability validation
* Industry research

Content should therefore emphasize **specific evidence and context**.

---

# 31. Metadata

Each project detail page should have:

* Unique title
* Unique meta description
* Canonical URL
* Appropriate Open Graph metadata

The title should identify the project and, where useful, the relevant sector or Asterra capability.

---

# 32. Image SEO

Project images should use:

* Descriptive filenames
* Meaningful alt text
* Responsive dimensions
* Efficient formats
* Appropriate loading behavior

Do not use keyword-stuffed filenames or alt text.

---

# 33. Structured Data

Where applicable, use structured data that accurately describes the page.

Possible relevant types depend on the actual project and content.

The priority is accurate representation rather than maximizing schema types.

---

# 34. Internal Linking

Strong relationships:

```text id="m9c4q6"
Project Detail
│
├── Projects Listing
├── Related Business Unit
├── Related Projects
└── Contact
```

Where relevant:

```text id="q5v8m2"
Project
  ↓
Business Unit
  ↓
Capability
```

This strengthens the site's information architecture.

---

# 35. Performance

Case studies can contain many large images.

Prioritize:

* Responsive image delivery
* Optimized image sizes
* Lazy loading below-fold gallery images
* Correct aspect ratios
* Efficient formats
* Minimal unnecessary scripts

The hero image should be prioritized appropriately.

---

# 36. Motion

Recommended:

```text id="x8k4m7"
Hero image
→ subtle entrance

Gallery
→ restrained transition

Project cards
→ subtle hover

Navigation
→ small directional movement
```

Avoid turning the case study into an animation showcase.

The project evidence must remain the focus.

---

# 37. Content Integrity

Do not invent:

* Client names
* Project values
* Locations
* Dates
* Results
* Metrics
* Project roles
* Testimonials
* Awards
* Certifications

If a project has limited information, create a concise project detail page rather than filling gaps with invented content.

# 40. Quality Gate

Before implementation:

### Story

* Does the page tell a coherent project story?

### Evidence

* Is there enough real information to justify a case study?

### Visuals

* Are the project images authentic and high quality?

### Clarity

* Can visitors understand Asterra's role?

### Outcomes

* Are results supported by evidence?

### Navigation

* Can users move to the capability and related projects?

### SEO

* Does the page have a clear, specific topic?

### Performance

* Are gallery assets optimized?

### Accessibility

* Can the complete case study be consumed without visual-only interactions?
