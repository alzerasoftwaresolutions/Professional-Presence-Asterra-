# Asterra Project / Case Study — Detailed Page Specification

**Package:** Package 3 — Professional Presence
**Template:** Template 01 — Corporate Authority
**Example Client:** Asterra Manufacturing Group
**Page:** Individual Project / Case Study Detail
**Route:** `/projects/[project-slug]`
**Version:** 1.0
**Status:** Design & implementation specification

> This specification follows the established Package 3 architecture, Universal Design Analysis, Template 01 — Corporate Authority, Asterra Design Manual, and the previously defined Projects Listing specification. SEO requirements use the **SEO Analytics & Optimization Playbook** as the universal reference, applying only what is relevant to an individual project/case-study page.

---

# 1. Page Purpose

The Project Detail page transforms the project portfolio from a list of claims into **evidence**.

The page should allow a prospective client to understand:

* What the project was
* Who it served
* Where it took place
* What Asterra's role was
* What challenge existed
* What Asterra did
* What capabilities were involved
* What was achieved

The page should answer:

> **Can Asterra successfully deliver work like this?**

---

# 2. Page Objectives

The page should:

* Present the project clearly.
* Establish credibility through real evidence.
* Explain Asterra's contribution.
* Demonstrate relevant capabilities.
* Communicate measurable outcomes where approved.
* Provide useful visual documentation.
* Connect the project to relevant business units.
* Connect the project to related insights.
* Support qualified commercial evaluation.
* Support organic search discovery.

---

# 3. Core Principle

The project page should **demonstrate rather than advertise**.

Weak:

> Asterra is a leading company delivering world-class solutions.

Stronger:

> Asterra provided engineering and implementation support for a new industrial processing facility, coordinating technical requirements across multiple project phases.

The page should prioritize evidence over promotional claims.

The H1 should be the official project name where possible.

# 17. Challenge Content Rules

The challenge should be specific.

Weak:

> The client needed a high-quality solution.

Stronger:

> The project required integration of multiple production requirements within an existing operational environment while maintaining continuity of operations.

Specificity creates credibility.

# 21. Approach Narrative

Each stage should explain actual work.

Example:

### 01 — Assessment

Understanding the operational requirements and project constraints.

### 02 — Design

Developing the technical solution according to the identified requirements.

### 03 — Implementation

Coordinating the approved solution across the relevant project activities.

### 04 — Validation

Testing and reviewing the delivered work.

### 05 — Handover

Supporting the transition to operational use.

Do not use these steps unless they accurately represent the project.

# 25. Gallery Rules

Use:

* Actual project imagery
* Approved technical visuals
* Relevant project documentation
* High-quality photography

Avoid:

* Generic stock photography
* Unrelated decorative images
* Repeated images
* Images with sensitive information

---

# 26. Image Captions

Use captions when they provide useful context.

Example:

> Installation phase at the project's processing facility.

Captions should not be mandatory for every image.

---

# 27. Image Alt Text

Alt text should describe meaningful image content.

Example:

> Asterra engineering team inspecting industrial equipment during installation.

Avoid:

> Asterra engineering project industrial facility engineering Ethiopia.

The latter is keyword stuffing.

Potentially relevant:

* `WebPage`
* `BreadcrumbList`
* `CreativeWork`

The schema should reflect the actual page content.

Do not claim a project is an `Article` simply for SEO benefit.

---

# 52. SEO — Canonicalization

Each project should generally have one canonical URL.

Avoid duplicate project pages created by:

* Filters
* Query parameters
* Multiple category paths
* Duplicate slugs

Filtered project listings should not accidentally create dozens of indexable duplicate pages.

# 54. SEO — Content Quality

A strong case study should contain enough unique information to provide genuine value.

Evaluate:

* Specificity
* Originality
* Evidence
* Accuracy
* Project context
* Asterra's role
* Outcome
* Relevant expertise

Avoid creating dozens of thin project pages with only:

> Project name + image + generic description.

---

# 55. SEO — Image Optimization

Use:

* Descriptive filenames
* Accurate alt text
* Responsive sizes
* Appropriate formats
* Compression
* Lazy loading for gallery images
* Optimized hero image

Do not load the entire full-resolution gallery immediately.

---

# 56. SEO — Performance

Project detail pages can become media-heavy.

Prioritize:

* Hero image optimization
* Gallery lazy loading
* Responsive image delivery
* Efficient font loading
* Minimal third-party scripts
* Stable layout dimensions
* Efficient video loading

---

* Hero readability
* Metadata layout
* Gallery behavior
* Image loading
* Long-form text
* CTA usability
